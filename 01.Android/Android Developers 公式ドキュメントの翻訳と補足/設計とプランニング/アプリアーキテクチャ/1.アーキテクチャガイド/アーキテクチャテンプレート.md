# アーキテクチャテンプレート

以下に Android（MVVM/クリーンアーキテクチャ）で使えるアーキテクチャテンプレートを示します。


# 1. プロジェクト全体方針

- レイヤー間の依存関係は 一方向 とし、循環依存を禁止する
- 各レイヤーは 明確な責務 を持ち、他レイヤーの責務を越境しない
- モデル（Domain/UI/Data）はレイヤーごとに定義し、責務に合わせて配置する
- マッピングは責務を持つレイヤーの中に置く（固定ルールではなく意味ベース）


# 2. レイヤー定義と責務

## 2-1. UI Layer（Presentation Layer）

### 責務

- 画面表示
- ユーザー操作の受け取り
- ViewModel による UI 状態管理
- UI 独自のモデル（UiState / UiModel）の定義
- UI 用の軽微なフォーマット変換
- UI モデル ↔ ドメインモデルのマッピング（必要な場合）


### UI に置かないもの

- ビジネスルール
- データ保存や API 呼び出し
- ドメインの意味を持つ変換ロジック

## 2-2. Domain Layer（UseCase + DomainModel）

### 責務

- アプリケーションの「意味・ルール・操作」の中心
- ユースケース（ドメインの操作単位）
- ドメインモデル（不変のビジネスルールを表す構造体）
- 変換ルールを含むバリューオブジェクトの生成（Price/DateRange など）


### Domain が行うマッピングの例

- `"1480"` → `Price(1480)`（ルールを持つ）
- `"2025-12-02"` → `Date(yyyy, mm, dd)`

※ 意味や制約がある場合のみ


### Domain に置かないもの

- UI 専用フォーマット（"1,480円" など）
- データソース依存のモデル（DTO, Entity）
- Android コンポーネント


## 2-3. Data Layer（Repository, DataSource, DB/Network）

### 責務

- 永続化、API 通信、データ取得などのインフラ処理
- 外部仕様（API, DB）の DTO や Entity の定義
- DTO/Entity ↔ ドメインモデルのマッピング
- キャッシュやページングなどのデータ管理戦略


### Data に置かないもの

- UI 表示用のフォーマット
- ドメインのビジネスルール
- UI 専用のモデル


# 3. 依存関係のルール

```
UI → Domain → Data  
UI → Data (直接依存はなるべく避ける)  
Data ↛ UI （禁止）  
Domain ↛ UI （禁止）  
Domain ↛ Data（禁止。Repository の interface は Domain に置く）
```


# 4. モデル・マッピングの配置方針（プロジェクト合意ポイント）

## UI モデル

UI 専用の見た目・状態 → UI レイヤーに置く。


## ドメインモデル

アプリの意味を持つ構造体 → Domain レイヤー。


## データモデル（Entity, DTO）

外部仕様に対応 → Data レイヤー。


## マッピング配置ルール（合意しておく）

### ① 見た目の差分（表示のためのフォーマット）

→ UI レイヤー

例：`"1480"` → `"1,480円"`


### ② 意味を持った値への変換（バリューオブジェクト生成）

→ Domain レイヤー

例：`"1480"` → `Price(1480)`


### ③ 外部仕様（API/DB）との変換

→ Data レイヤー

例：`PaymentEntity(amountInt)` → `Payment(amount: Price)`


# 5. テスト方針（レイヤーごと）

- UI：ViewModel の状態遷移テスト
- Domain：ユースケース・バリューオブジェクトのロジックテスト
- Data：Repository の通信処理テスト


# 6. パッケージ構成のテンプレート（Android 用）

```
com.example.project
 ├── ui/
 │    ├── screenA/
 │    ├── screenB/
 │    └── common/
 ├── domain/
 │    ├── model/
 │    └── usecase/
 └── data/
      ├── repository/
      ├── datasource/
      ├── api/
      └── db/
```


# 7. プロジェクト独自のルール（最後にチームで決める部分）

- UI ↔ Domain マッピングを UI に置くか Domain に置くか？
- UseCase にどこまでロジックを置くか？
- Repository のインターフェイスを Domain に置くか？
- ViewModel のパッケージ構成はどうするか？

これらはチームの方針に合わせて調整。
