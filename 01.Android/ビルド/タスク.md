# タスク

## タスクの登録（register）

タスクを登録するには、 register 関数を呼び出します。以前までは、 create 関数を呼び出して登録することもありましたが、現在は register で登録する方法が一般的です。 register 関数は、遅延登録に対応しており、ビルドパフォーマンスが良いです。

register 関数を呼び出す際は、 tasks インスタンスの関数を直接呼び出すか、 Kotlin DSL を使用して呼び出すことが可能です。

```kotlin
// 方法１ : tasks インスタンスの関数を直接呼び出す
tasks.register("hello") {
    // do something.
}

// 方法２ : Kotlin DSL を使用して呼び出す
tasks {
    register("hello") {
        // do something.
    }
}
```

Kotlin DSL では、 register 関数を呼び出す際に、タスク型を指定することが可能です。

```kotlin
tasks.register<Copy>("copyHello") {
    // do something.
}

tasks {
    register<Copy>("copyHello") {
        // do something.
    }
}

val copyHello by tasks.registering("copyHello", Copy::class) {
    // do something.

    // この記述方法は、 by registering() 構文を使う Kotlin DSL のシンタックスシュガーです。
    // 上記の二つの記述方法とほぼ同じ意味になります。
}

val copyHello by tasks.registering(Copy::class) {
    // do something.

    // タスク名は、デフォルトで変数名となります。
}
```


### 定義済みのタスク型

上記の Copy 型のように、 register 関数に渡す型パラメータが最初からいくつか定義されています。型付きタスクを使うと、補完が効くため設定ミスが減ったり、キャストなしで便利な関数が使用できます。


### ファイル操作系

```kotlin
// Copy タスク：ファイルやフォルダをコピー
tasks.register<Copy>("copyApk") {
    from("build/outputs/apk/debug/app-debug.apk")
    into("backup/")
}

// Delete タスク：古いファイルを削除
tasks.register<Delete>("cleanBackup") {
    delete("backup/")
}

// Sync タスク：ディレクトリを同期
tasks.register<Sync>("syncAssets") {
    from("src/main/assets")
    into("build/assets")
}
```


### 外部コマンド・Java 実行系

```kotlin
// Exec タスク：外部コマンド実行
tasks.register<Exec>("runScript") {
    commandLine("sh", "scripts/deploy.sh")
}

// JavaExec タスク：Java プログラムを実行
tasks.register<JavaExec>("runTool") {
    mainClass.set("com.example.tools.Main")
    classpath = sourceSets["main"].runtimeClasspath
}
```


### アーカイブ系

```kotlin
// Zip タスク：複数ファイルを ZIP 圧縮
tasks.register<Zip>("zipBackup") {
    from("backup/")
    destinationDirectory.set(layout.buildDirectory.dir("archives"))
    archiveFileName.set("backup.zip")
}

// Jar タスク：Java / Kotlin コードの JAR を生成
tasks.register<Jar>("jarLib") {
    from(sourceSets["main"].output)
    archiveBaseName.set("mylib")
    archiveVersion.set("1.0")
}
```

`PackageAndroidArtifact` というタスク型もあります。これは APK や AAB をパッケージングするタスクです。

`GenerateBuildConfig` というタスク型もあります。これは BuildConfig.java を生成するタスクです。


### テスト・Lint 系

```kotlin
// Test タスク：JUnit テスト
tasks.register<Test>("unitTest") {
    testClassesDirs = sourceSets["test"].output.classesDirs
    classpath = sourceSets["test"].runtimeClasspath
}

// Android Lint タスク（既存タスクに依存追加例）
tasks.named<AndroidLint>("lint") {
    doLast {
        println("Lint check completed")
    }
}
```

`AndroidUnitTest` というタスク型もあります。これは、その名の通り、単体テスト用タスクです。

Android 特有のタスク型 (以下の 4 つ) は、自作で register するよりも 既存タスクに依存関係を追加 したり、 doLast をフックして処理を追加する形で使います。

- AndroidUnitTest
- AndroidLint
- PackageAndroidArtifact
- GenerateBuildConfig


## タスクの実行

### CUI で実行

Android Studio のコマンドラインから実行する場合は以下のようになります。

```bash
./gradlew <タスク名>

# 例
./gradlew clean
```

Windows のターミナルから実行する場合は以下のようになります。

```bash
gradlew.bat <タスク名>

# 例
gradlew.bat clean
```

複数タスクをまとめて実行する場合は以下のようになります。

```bash
./gradlew <タスク名> <タスク名>

# 例
./gradlew clean assembleDebug
```


### GUI で実行

Android Studio の GUI から実行する場合は以下のようになります。

右側の Gradle タブを開く > "Gradle" > プロジェクト名 > Tasks > build や other の中から実行したいタスクをダブルクリック



### 別のタスクから実行（dependsOn）

Gradle スクリプト（build.gradle.kts）内から別のタスクを実行したい場合は、依存関係を定義します。

```kotlin
tasks.register("copyAndClean") {
    dependsOn("clean", "copyApk")
}
```

上記の場合、 copyAndClean タスクを実行すると、 clean → copyApk の順に自動で実行されます。


### CI から実行

GitHub Actions などの CI から実行することも可能です。詳細は、時間があるときに別紙にまとめます。 GitHub Actions から実行する場合は、以下のような YAML ファイルを .github/workflows/build.yml に配置して、 GitHub にプッシュします。自動実行されるためのトリガーなども別途指定する必要があります。

```yaml
- name: Run custom Gradle task
  run: ./gradlew copyApk
```


## タスクの実行オプション

タスクをターミナルから実行する際に、ハイフン二つでオプションを指定することが可能です。以下は `--profile` というオプションを付加した例です。

```bash
./gradlew build --profile
```

主なオプションを以下に紹介します。これらのオプションは、 build タスクに限らず、全てのタスクで指定可能です。

- 解析系
  - `--profile` オプション
    -  ビルド時間の内訳を確認できる。ビルドのどのタスクに時間がかかっているか分析可能。
  - `--dry-run`
    - 実際には実行せず、タスクの実行順序を確認。
  - `--info`
    - 通常のビルドログよりも詳しい情報を出力します。
    - 「どのタスクが実行されたか」「依存関係の解決」「簡単な警告」などが表示されます。
  - `--debug`
    - --info よりさらに詳細な情報を出力します。
    - Gradle の内部処理や、キャッシュ・依存関係の解決など、デバッグ用の情報もすべて表示されます。
  - `--scan`
    - 実行するとブラウザで確認できるリンクが出力され、タスク実行時間、依存関係、警告、キャッシュヒット率などをグラフィカルに確認可能
- 高速化系
  - `--build-cache`
    - ローカル／リモートキャッシュ利用。
  - `--parallel`
    - モジュール間の並列ビルド。

## タスクの前処理（doFirst）と後処理（doLast）

タスクの前処理を定義するには、 `doFirst` 関数を使用し、後処理を定義するには、 `doLast` 関数を使用します。

```kotlin
tasks.register<Copy>("copyFiles") {
    doLast {
        println("コピーを開始します！")
    }

    from("src")
    into("dest")

    doLast {
        println("コピー完了しました！")
    }
}
```

上記の例では、 copyFiles タスクの実行前に `"コピーを開始します！"` が出力され、コピーの完了後に `"コピー完了しました！"` が出力されます。

doFirst と doLast は、 Task インスタンスの関数であるため、 Task インスタンスが参照できるスコープ内でのみ呼び出すことができます。主なスコープを以下に紹介します。

### named 関数内

named 関数は、既存タスクを取得して設定を追加する関数です。

```kotlin
tasks.named("myTask") {
    doFirst { println("後から先頭追加") }
    doLast { println("後から末尾追加") }
}
```


### withType 関数内

withType 関数は、指定したタスク型すべてに対して設定を追加する関数です。

```kotlin
tasks.withType<Copy> {
    doLast { println("すべてのCopyタスクの末尾処理") }
}
```

上記の例では、プロジェクト内のすべての Copy タスクに対して、後処理が追加されます。 withType は、遅延評価されるため、 register 関数で追加される Copy タスクにも適用されます。

name 関数のように個別に設定する必要がないため、設定忘れを防ぐことができます。


### getByName 関数で Task を取得して呼ぶ

`tasks.getByName("タスク名")` などで `Task` を取得して doFirst や doLast を呼ぶことも可能です。

```kotlin
val t = tasks.getByName("myTask")
t.doFirst { println("直接取得して先頭") }
t.doLast { println("直接取得して末尾") }
```


## よく使用される定義済みのタスク

定義済みのタスクがどのようなタスクなのかを理解しておくと、 CI などで自動化する際に、必要なタスクのみ実行するのに役立ちます。


### ビルド関連

- assemble 系
  - `assembleDebug` : デバッグ APK をビルド
  - `assembleRelease` : リリース APK をビルド
  - `assemble` : すべてのビルドバリアントの APK をビルド
- build 系
  - `build` : コンパイル、テスト、APK 作成など、通常のビルド処理を一括で実行
- clean
  - `clean` : ビルド成果物（build フォルダ）を削除


### テスト関連

- test 系
  - `testDebugUnitTest` : ユニットテスト（ローカル JVM）をデバッグバリアントで実行
  - `testReleaseUnitTest` : ユニットテストをリリースバリアントで実行
- connectedAndroidTest
  - `connectedAndroidTest` : 実機またはエミュレーターでの UI テスト（Instrumentation Test）を実行


### デプロイ・インストール関連

- install 系
  - `installDebug` : デバッグ APK を接続中のデバイスにインストール
  - `installRelease` : リリース APK をインストール（署名済みが必要）
- uninstall 系
  - `uninstallDebug` : デバッグ APK をアンインストール
  - `uninstallRelease` : リリース APK をアンインストール


### 依存関係・同期関連

- `dependencies` : プロジェクトの依存関係ツリーを表示
- `buildEnvironment` : Gradle の環境情報を表示


### その他よく使うユーティリティ

- `tasks` : 使用可能なタスク一覧を表示
- `help` : Gradle コマンドのヘルプ表示
- `lint` : Android Lint を実行してコード品質や警告をチェック
- `assembleAndroidTest` : テスト APK をビルド


## ビルドバリアント固有のタスクを定義する

ビルドバリアントを意識せずに定義したタスクは、すべてのビルドバリアントで共通のタスク（処理）となります。共通の処理ではうまく実行できない場合があります。例えば、 `build/outputs/apk/freeDebug/app-freeDebug.apk` のようなファイルにアクセスしたい場合、単純に `build/outputs/apk/` を見に行くと、バリアントによってパスが違うので、共通タスクだけではアクセスできません。そのような場合は、バリアントごとにタスクを変更する必要があります。

以下の例では、 all 関数を使用して、全てのバリアントをループ処理しています。

```kotlin
android.applicationVariants.all { variant ->
    tasks.named("myTask") {
        doLast {
            println("Running for ${variant.name}")
        }
    }
}
```

ライブラリの場合は、 `applicationVariants.all{}` の代わりに `libraryVariants.all{}` が使えます。

既存のタスクは、全てのビルドバリアントに対応するように定義されているため問題ありません。自分でタスクを定義する場合のみ、ビルドバリアントごとにタスクを定義する必要があるかどうかを意識する必要があります。
