# 依存関係の競合を解決する

## 概要

依存関係の競合とは何か、具体例を挙げながら説明します。

- まず、依存関係の競合は、アプリ内でライブラリを使用している場合にのみ、発生する可能があります。
- 例えば、自分のアプリ ( app モジュール) が LibraryA というライブラリを使用していたとします。
- 自分のアプリ ( app モジュール) も LibraryA も Retrofit ライブラリに依存していたとします。
- app モジュールでは、バージョン 2.9.1 の Retrofit に依存していたとします。
- LibraryA では、バージョン 2.9.0 の Retrofit に依存していたとします。

このような状況を **依存関係の競合** と呼びます。

Android の仕組みとして、基本的には、一つのアプリ内で同一のアーティファクト ID (この例では Retrofit) に対して、複数のバージョンの依存関係を構築することはできません。

そのため、バージョンをどちらかに統一する必要があります。これを **依存関係の競合の解決** と呼びます。


## リモートリポジトリからライブラリを取得している場合

### 基本的な競合解決

リモートリポジトリからライブラリ (上記の例でいう LibraryA にあたるもの) を自動取得している場合は、 Gradle が自動的に、より新しいバージョンの依存関係を採用するように動作します。

これは、 LibraryA.aar と一緒に .pom というファイルをダウンロードしているおかげです。 .pom ファイルは、 LibraryA がどのアーティファクト ID のどのバージョンに依存しているかを記述しているファイルです。以下は .pom ファイルの例です。

```
<project>
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>LibraryA</artifactId>
    <version>1.0.0</version>
    <dependencies>
        <dependency>
            <groupId>com.squareup.retrofit2</groupId>
            <artifactId>retrofit</artifactId>
            <version>2.9.0</version>
        </dependency>
    </dependencies>
</project>
```

これは、 LibraryA がバージョン 2.9.0 の Retrofit に依存していることを意味します。


### バージョンを自分で指定したい場合

もし、アプリ側で 「 Retrofit は必ず 2.9.0 を使いたい」 としたい場合は、 `resolutionStrategy` を使って指定できます。

```kotlin
configurations.all {
    resolutionStrategy {
        force("com.squareup.retrofit2:retrofit:2.9.0")
    }
}
```

これを app/build.gradle.kts に書くと、ライブラリがどのバージョンを要求しても 2.9.0 に統一されます。


## 手動でライブラリを取得している場合

手動でライブラリ ( .aar や .jar ) を取得している場合、その中に .pom ファイルは含まれていません。そのため、ライブラリ ( LibraryA ) にどのような依存関係が存在するのかが、 Gradle は全くわかりません。 

そのため、ライブラリの使用者は、ライブラリの README などを参照して、そのライブラリが 「どのアーティファクト ID のどのバージョン」 に依存しているのかを確認する必要があります。もし書かれていなければ、 jadx や zip で .aar を展開し、 classes.jar 内から Retrofit , OkHttp などのバージョンを推測することが可能です。

そして、 Gradle の自動調停方針と同じように、より新しいバージョンでコンパイルして、動作確認をしましょう。それで問題が検出されなければ、そのバージョンを使用することがおすすめです。より新しいバージョンを採用することで、他のライブラリなどと歩調を合わせやすかったり、非推奨のコードが含まれている可能性を下げることができます。


## 【豆知識】ライブラリを取り込むときにライブラリの依存関係をアプリ側で定義する必要があるのか

LibraryA というライブラリが Retrofit に依存していたとします。この LibraryA を依存関係に持つアプリ ( app モジュール) は、 Retrofit への依存関係を app モジュールの build.gradle.kts に定義する必要はあるのでしょうか？

答えは、「 .pom ファイルが存在しない場合は、定義する必要がある」です。

.pom ファイルは、ライブラリの依存関係をライブラリの利用者側に伝えるためのファイルです。このファイルが存在していれば、 Gradle は、ライブラリの依存関係を知ることができるため、 Gradle がそれらの依存関係を自動的に解決してくれます。よって、改めてライブラリの利用側でそれらの依存関係を定義する必要はありません。

LibraryA は、ビルドして .aar や .jar が生成される際に、その build.gradle.kts に Retrofit への依存関係を定義していますが、この情報は .aar や .jar には含まれません。そのため、 app モジュールで LibraryA を取り込む際に、再度、 Retrofit への依存関係を定義する必要があります。その際に、 .pom ファイルが存在していれば、 Gradle が自動的に依存関係を追加してくれるということです。

その一方で、 Fat AAR というものもあり、 Fat AAR は、ライブラリの依存関係を .aar に含めます。そのため、ライブラリの利用側でライブラリの依存関係を定義しなくてもライブラリが動作します。ただし、 Gradle が Fat AAR の依存関係を知るすべがないため、ライブラリの利用側で異なるバージョンの依存関係が定義されると、どちらの依存関係が使用されるかが不明確となり、予期せぬクラッシュの危険性があります。


## 最終的に採用されたバージョンを確認する

リモートリポジトリから取得しているライブラリが存在する限り、 Gradle による自動的な競合解決が実施されている可能性があります。つまり、 build.gradle.kts に記述したバージョンとは異なるバージョンが採用されている可能性があるということです。そのため、最終的にどのバージョンのライブラリが採用されたのかを確認するには、 build.gradle.kts を見ただけではわかりません。

最終的に採用されたバージョンを確認するには、 Gradle のコマンド（タスク）を実行して、バージョン一覧を出力します。コマンド（タスク）には、様々なものが用意されていますが、基本的には、以下のコマンドを使用します。

```bash
./gradlew :dependencies
```

このコマンドを実行すると以下のような出力が得られます。

```lua
+--- project :mylib
|    \--- com.squareup.retrofit2:retrofit:2.9.0 -> 2.9.1
|         +--- com.squareup.okhttp3:okhttp:3.14.9
|         \--- com.squareup.okio:okio:1.17.2
+--- project :mylib2
|    \--- com.squareup.retrofit2:retrofit:2.9.1
|         +--- com.squareup.okhttp3:okhttp:3.14.9
|         \--- com.squareup.okio:okio:1.17.2
\--- com.squareup.retrofit2:retrofit:{conflict resolved to 2.9.1}
```

これは、 mylib の retrofit に 2.9.0 のバージョンが要求されたが、最終的には 2.9.1 のバージョンを採用したことを意味します。


### 対象範囲を限定する

上記の `dependencies` コマンドで、依存関係グラフを出力すると膨大な量の依存関係が出力されます。膨大な依存関係グラフは、バージョン確認作業を煩雑にしてしまうため、対象範囲を限定してコマンドを実行することをお勧めします。

以下は、依存関係グラフの出力範囲を app モジュールに限定する例です。

```bash
./gradlew :app:dependencies
```

以下は、依存関係グラフの出力範囲を実行時に必要な実行時に必要な依存関係に限定する例です。

```bash
./gradlew :dependencies --configuration runtimeClasspath
```

`--configuration` オプションに指定可能な引数で主要なものを以下に示します。

| 構成名                             | 説明                                                                   |
| ---------------------------------- | ---------------------------------------------------------------------- |
| debugCompileClasspath              | `debug` ビルド時にコンパイル対象となる依存関係                         |
| releaseCompileClasspath            | `release` ビルド時にコンパイル対象となる依存関係                       |
| debugRuntimeClasspath              | `debug` 実行時（APK 実行時）に必要な依存関係                           |
| releaseRuntimeClasspath            | `release` 実行時に必要な依存関係                                       |
| implementationDependenciesMetadata | `implementation` で指定された依存関係のメタ情報                        |
| apiDependenciesMetadata            | `api` で指定された依存関係のメタ情報（主にライブラリモジュールで使う） |
| annotationProcessor                | Java/KAPT のアノテーションプロセッサ関連の依存関係                     |
| kaptDebug / kaptRelease            | Kotlin KAPT 用のアノテーションプロセッサ依存関係                       |
| testCompileClasspath               | 単体テスト (`test/`) のコンパイル用依存関係                            |
| testRuntimeClasspath               | 単体テストの実行時に必要な依存関係                                     |
| androidTestCompileClasspath        | インストルメンテーションテスト (`androidTest/`) のコンパイル用依存関係 |
| androidTestRuntimeClasspath        | インストルメンテーションテスト実行時に必要な依存関係                   |

build.gradle.kts の dependencies ブロック内で依存関係を定義する際に、 `implementation` , `api` , `compileOnly` , `runtimeOnly` のどれにするかや、 debug ビルドなのか release ビルドなのか等によって、上記の構成がどれになるかが決まります。

`implementation` や `api` の違いなどについては、 [dependencies ブロックのコンフィギュレーションの説明](./BuildGradleの具体的な使用方法.md/#dependencies-ブロックのコンフィギュレーションの説明) を参照してください。
