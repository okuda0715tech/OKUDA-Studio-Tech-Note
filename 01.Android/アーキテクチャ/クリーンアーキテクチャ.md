# クリーンアーキテクチャ

## 1. クリーンアーキテクチャの本質

クリーンアーキテクチャは、クラス配置やモジュール分割の手法ではなく、 **「意味的な依存関係（本質と詳細の関係）」** を表した考え方です。

円形の図が伝えたいのはただ一つ：

- 中心にあるものほど **本質**
- 外側にあるものほど **詳細**
- **本質は詳細に依存しない**

これはそのまま、

- 抽象は具体に依存しない
- 本質は実装に依存しない

というオブジェクト指向の原則と一致します。


## 2. 意味的依存関係とは何か

意味的依存関係とは：

- 「どちらがどちらに合わせるか」
- 「変更が来たとき、どちらが影響を受けるべきか」
- 「どちらが因で、どちらが果か」

という **因果・責務・変更理由の依存** です。

クリーンアーキテクチャ的には

- Domain
  - 現実世界の意味・ルール（本質）

- UI / DB / Framework
  - 表現方法・保存方法・技術（詳細）

👉 UI や DB は Domain に意味を合わせる
👉 Domain は UI や DB に意味を合わせない

この関係性そのものが「意味的依存」です。


## 3. 物理的依存関係との違い

物理的依存関係

- import
- 型参照
- モジュール依存
- build 依存

👉 コンパイラや IDE が扱う依存


## クリーンアーキテクチャが問題にするのは？

👉 物理的依存そのものではなく、その裏にある意味的依存が正しいかどうか

物理的依存は「実装上の制約そのもの」を作り、意味的依存は「本質と詳細の関係」を表すものです。


## 4. 制御の流れとの関係

クリーンアーキテクチャでは、次の3つを分けて考えます。

- 意味的依存
  - 本質と詳細の関係
  - Domain が中心

- 制御の流れ
  - 実行時に処理がどこからどこへ進むか
  - UI → Domain → Data

- ソースコード依存（物理的依存）
  - import の向き
  - 制御の流れと一致してもよいし、しなくてもよい

重要な主張はこれです：

**制御の流れとソースコードの依存関係は逆転してもよい**

これは、

**意味的依存を守るためなら、物理的依存は逆転させてよい**

と言い換えられます。


## 5. UI → Domain → Data の正体

よく言われる

```
UI → Domain → Data
```

は、

- **制御の流れの話**
- **物理的依存をどう張るかの話**

です。

一方で、

- **意味的依存** は

```
Domain ← UI
Domain ← Data
```

になっています。

このズレを解消するために使われるのが：

- インターフェース
- 依存関係逆転（DIP）
- Repository パターン

です。

## 6. Repository と Mapper が「境界」になる理由

**Repository**

- Domain は「保存する」という概念だけを知る
- Data 側が Domain に合わせて実装する
- だから interface を Domain 側に置き、実装は Data 側に置く
  - interface は Domain が定義するものであり、 Domain の所有物である
  - Data 側の interface の実装者が変わっても interface には影響がないことからもそれは明らか

👉 意味的依存を守るための構造

**Mapper**

- 両レイヤーのモデルを知っている
- 境界そのものを実装している
- 「合わせに行く」責務を持つ

👉 Mapper は、意味的依存を物理的依存に落とす翻訳層

だから特殊であり、物理的配置だけで善悪は決まらない。


## 7. 意味的依存と物理的依存は混在してよいのか？

問題ありません。必ず混在します。

重要なのは、混在していることではなく

- どこが境界かを説明できること
- どちらがどちらに合わせているかを言語化できること


## 8. クリーンアーキテクチャにおける意味的依存

覚える必要はありません。この問いだけで十分です。

「このコードは、どちらがどちらに合わせているか？」

- UI / Data が Domain に合わせている → 正しい
- Domain が UI / Data に合わせている → 危険信号


## 9. クリーンアーキテクチャの正体（まとめ）

- クリーンアーキテクチャは、意味的依存関係（本質と詳細）を可視化したもの
- 円形の図は、制御の流れや import の図ではない
- 物理的依存や制御の流れは、意味的依存を守るために、インターフェースを使って調整されることがある
- 理解のゴールは、ルールを覚えることではなく、因果で判断できること

最後に一文で言うなら

クリーンアーキテクチャとは、「何が本質で、何が詳細か」をコードの物理的な依存関係で、嘘なく表現し続けるための思想である。
