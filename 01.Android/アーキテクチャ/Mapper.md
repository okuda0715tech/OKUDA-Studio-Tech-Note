# Mapper

## 6. Mapper はなぜ「意味的依存を物理的依存に落とす翻訳層」なのか

ここ、丁寧に行きます。

### ① 意味的依存だけなら、世界はきれい

Domain は本質

Data / UI は詳細

「合わせる方向」は明確

でもコードは：

型を参照しなければならない

値をコピーしなければならない

null / enum / ID / 表示形式を扱わなければならない

👉 意味だけでは動かない

### ② Mapper がやっていること

Mapper は：

Domain の意味を壊さずに

Data / UI の制約に合わせる

具体的な型変換を引き受ける

例：

nullable → non-null

ID → ValueObject

enum → 表示用文字列

👉 物理的には両側を import せざるを得ない


### ③ なぜ「特殊」なのか

両レイヤーの型を知っている

両側が変わると壊れる

でも 境界がここにあると分かっていれば被害は局所化する

つまり：

Mapper は
「意味と実装のズレが必ず集約される場所」


### ④ だから配置だけで善悪は決まらない

重要なのは：

Mapper が

Domain に入り込んで意味を汚していないか

UI / Data に引きずられていないか

Mapper が

「合わせに行く」責務を引き受けているか

👉 置き場所より、責務の向き


## 7. 最後に一段深い整理（あなた向け）

あなたの言葉で言い換えるなら：

インターフェースとマッパーは、
「意味的依存を守るために、
物理的依存の歪みを一身に引き受ける装置」

です。

だから：

不思議に見える

特殊に見える

でも無いと設計が崩れる
