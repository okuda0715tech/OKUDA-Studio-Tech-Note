# UI設計チェックリスト（判断・状態・責務の境界）

このチェックリストは、 **「判断がどこで完了しているか」** と **「状態が嘘をついていないか」** を確認するためのものです。

Jetpack Compose / ViewModel / Repository など、 **どの層でも共通して使える設計確認リスト** としてまとめています。

---

## 1. 判断の完了チェック

- [ ] 境界（Repository → VM / VM → UI）を越える前に、判断は完了しているか
- [ ] 受け取った側は「これ以上の場合分け」を必要としていないか
- [ ] if / when の条件に `&&` や `||` が頻出していないか
- [ ] if のネストが「状態の組み合わせ」を表そうとしていないか

👉 **判断とは「完全に場合分けが完了していて、それ以上場合分けが不要な状態」を作ること**

---

## 2. 状態の正確性チェック（嘘をつかないか）

- [ ] その状態は「ありえない組み合わせ」を表現できてしまわないか
- [ ] 状態の意味をコメントで補足していないか
- [ ] フィールドの組み合わせを見ないと意味がわからない状態になっていないか
- [ ] 状態の数が増えると破綻しそうな構造になっていないか

👉 **状態は「正確に・単独で意味を表せる」ことが重要**

---

## 3. Boolean 使用チェック

- [ ] Boolean は「すでに判断が完了した結果」か
- [ ] 他の状態と組み合わせないと意味を持たない Boolean になっていないか
- [ ] Boolean の意味を変数名だけに頼っていないか
- [ ] 将来 true/false 以外の状態が増えそうではないか

👉 **Boolean が「判断材料」になった瞬間に設計崩壊が始まる**

---

## 4. UI の責務チェック

- [ ] UI は「表示するだけ」になっているか
- [ ] UI 側で状態を合成・変換・解釈していないか
- [ ] UI の when は「表示結果が確定した状態」を受け取っているか
- [ ] UI の条件分岐が仕様理解を必要としていないか

👉 **UI は判断者ではなく、表現者であるべき**

---

## 5. ViewModel の責務チェック

- [ ] UI に渡す状態は ViewModel で確定させているか
- [ ] map / combine で「意味のある状態」に変換しているか
- [ ] UI が計算しなくても済む形になっているか
- [ ] ViewModel が「判断の集約点」になっているか

👉 **ViewModel は「判断を完了させる層」**

---

## 6. Repository 設計への応用チェック

- [ ] Repository が「生データ」だけを返していないか
- [ ] 呼び出し側で毎回同じ判断をしていないか
- [ ] ドメイン上の意味を Repository で表現できているか
- [ ] Entity / Result が判断済みの形になっているか

👉 **Repository でも「判断漏れ」は同じ問題を引き起こす**

---

## 7. 違和感センサー（最重要）

- [ ] 読んでいて「なんか分かりにくい」と感じないか
- [ ] 条件分岐を頭の中で整理し直していないか
- [ ] 修正時に影響範囲を広く追う必要がありそうか

👉 **違和感 = 判断がどこかで漏れているサイン**

---

## まとめ（設計の合言葉）

- 判断は境界を越える前に完了させる
- 状態は嘘をつかせない
- UI は解釈しない
- Boolean は結果として使う
- 違和感を無視しない

このチェックリストに引っかかったら、 **「判断を一段手前で完了できないか？」** を必ず考える。
