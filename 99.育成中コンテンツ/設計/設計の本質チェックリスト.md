
# 設計の本質チェックリスト

（責任分担 × 依存関係の方向）

## 1. 責任分担チェック（Separation of Concerns）

* このクラス／関数は **「何を決める存在か」** を一文で説明できる
* 「どうやるか（手段）」と「何をやるか（判断）」が混ざっていない
* 名前を読んだだけで責務が想像でき、コメントで補足していない
* if / when が増えている理由が「分岐」ではなく「責務の混在」になっていない
* UI が

  * 状態を *判断* していない
  * ビジネスルールを *解釈* していない
* Repository / UseCase が

  * 表示都合（UI用の整形）を知らない
  * フレームワークの型（Context, View, Composable）を知らない
* 「便利だから」という理由で責務を増やしていない
* その責務は **他の場所に置いたらおかしいか？** と自問して YES になる

---

## 2. 依存関係の方向チェック（Dependency Direction）

* 依存の矢印を図にしたとき、一方向に流れている
* 上位概念（ルール・方針）が下位詳細（実装）を import していない
* 「安定しているもの」が「不安定なもの」に依存している
* フレームワークを外したとき、

  * Domain / UseCase が残る
  * 仕様の説明ができる
* インターフェースは

  * **使う側の都合**で定義されている
  * 実装の都合で生まれていない
* テストで

  * 上位層が下位層をモックできる
  * 逆は必要ない

---

## 3. 変更耐性チェック（設計の成果）

* 仕様変更が起きたとき

  * 修正箇所を「ここ」と即答できる
* UI変更で

  * Domain / UseCase に手を入れなくて済む
* データ取得方法変更で

  * UIや判断ロジックが壊れない
* 新しい機能追加が

  * 既存コードの修正ではなく「追加」で済む
* 削除したとき

  * 影響範囲が予測どおりに狭い

---

## 4. 危険サイン（設計が崩れ始めている兆候）

* 「ここに書くのは微妙だけど…」という前置きが増える
* DTO / Model が万能オブジェクト化している
* UI層に

  * null判定の意味
  * 状態遷移のルール
    が集まり始めている
* Repository が

  * if / when だらけ
  * 仕様判断を持ち始めている
* テストが

  * 書けない理由の説明で長くなる

---

## 5. 最終問い（これだけで8割見抜ける）

* **このコードは「判断」をしているか？それとも「実行」しているだけか？**
* **この依存は「変わりやすいもの → 変わりにくいもの」になっていないか？**
* **この責務は、他の場所に移すと違和感が減らないか？**

---

# まとめ（本質の再確認）

> **設計とアーキテクチャの本質は
> 「責任を正しく分け、その責任同士を壊れない向きでつなぐこと」**
