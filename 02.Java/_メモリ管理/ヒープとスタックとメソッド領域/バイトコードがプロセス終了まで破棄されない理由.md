# バイトコードがプロセス終了まで破棄されない理由

理由は **破棄するメリットよりもデメリットの方が圧倒的に大きい** からです。

もっと具体的には、以下 3 つが決定的な理由です：


## 【理由1】バイトコードは極端に小さいので、解放する必要がない

- 関数1個あたり → ほんの数百〜数千バイト
- クラス1個あたり → 数 KB〜数十 KB
- 大規模アプリでも → 合計で数 MB 程度

Android のプロセスは普通 100〜300MB ほど のメモリを使えるので、
バイトコードが何 MB 残っていようが 全く問題にならない。

**解放しても節約できるのは数 MB。**

一方で、解放に伴うコスト（後述）はずっと大きい。


## 【理由2】バイトコードを再ロードする方がコストが高すぎる

もし一度使ったクラスを破棄すると…

次にそのクラスの関数を呼んだときに：

1. クラスファイルをストレージから読み直す
2. クラスを検証（verification）する
3. リンクする
4. メソッドテーブルを再構築
5. 参照関係を最適化する
6. 必要なら JIT コンパイル（ネイティブコード生成）し直す

**これらは「メモリ数 KB の節約」よりも 圧倒的に重い処理。**

つまり：

- バイトコードの再ロードは高コストすぎて非現実的
- 一度ロードしたクラスはプロセス終了まで持ち続けるのが最適解


## 【理由3】クラスを破棄すると、JIT が最適化できなくなる

Android では ART による JIT（Just-In-Time）コンパイル が走ります。

- よく実行されるメソッドはネイティブコードへ最適化
- 実行パスを解析して高速化
- インライン化（関数の埋め込み）も可能

もしバイトコードを途中で破棄すると：

- JIT の最適化結果も破棄する必要がある
- 再度最適化が必要
- 実行パフォーマンスが落ちる

**JIT の効果を最大化するためにも、クラスは保持し続けるのが合理的。**
