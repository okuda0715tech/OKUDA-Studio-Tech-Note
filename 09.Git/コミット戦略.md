# コミット戦略

コミット戦略、特にコミットの粒度について考えた内容をまとめます。


## コミットの粒度は小さく

コミットの粒度は、基本的には小さければ小さいほど良いと考えています。その理由は、レビューがしやすくなるためです。

誰かにレビューしてもらう場合も、自分で自分のコードをレビューする場合でも、コミットの粒度が小さいほどレビューがしやすいと考えています。一つのコミットにたくさんの修正が含まれていると、以下のようなデメリットがあります。

- レビューが終わったところが、何度も目に入ってくるので、何度も重複レビューしてしまい、効率が悪くなる。
- どこまでレビューが終わったのかがわからなくなり、レビュー漏れが発生するリスクがある。
- 様々な目的の修正が一つのコミットにまとまっているため、混乱する。

人間の脳が一度に把握できる内容には限界があるため、粒度の大きなコミットは、誰がレビューしたとしても、上記のようなデメリットが必ず発生します。


## コミット粒度が大きくなってしまった場合

それでも、一つのまとまった修正単位でのコミットを意識していると、どうしても、コミット粒度が大きくなってしまうことがあります。

その際は、 hunk と呼ばれる部分コミット機能を使用して、粒度の小さいコミットになるようにしましょう。未コミットの状態なら、部分コミットは可能です。


### 部分コミットのやり方

Android Studio なら、 diff を開いて、コードの行数の部分にあるチェックボックスをチェックするとそこだけをステージングすることができます。

部分コミットで、今回はコミットしないことにしたコードは、一度スタッシュして、ビルドが通るか確認しましょう。


### 部分コミットしたものをビルドしたらエラーが出た場合

コミット済みの場合は、一度、リセットして、部分コミットしたものをステージングに戻しましょう。

その後、 change list を変更して、部分コミット対象の change list とは、別の change list にスタッシュした内容を復元しましょう。

「部分コミット対象の change list 」 と 「対象外の change list 」 をそれぞれ修正しましょう。

コミット対象のものだけコミットし、対象外の部分はスタッシュして、再度、ビルドが通るか確認しましょう。

ビルドが通れば、スタッシュしたものを復元して、これの繰り返しをしていき、粒度の小さいコミットを実現していきます。


## コミットの粒度を小さくしたら未実装の機能は TODO コメントすれば OK

コミットの粒度を小さくしていくと、一つの機能が完成する前にコミットすることもでてきます。しかし、これは TODO コメントを記載したうえでコミットしてしまって問題ありません。なぜなら、未実装の機能があることよりも、変更が巨大化してしまうことの方がデメリットが大きいからです。変更が巨大化してしまうと、不完全なレビューにつながり、不具合の温床になります。一方で、未実装の機能は、試験項目に不足がなければ、多くの場合、発見できます。また、実装者自身も「実装予定の機能一覧」と照らし合わせながら、どの機能が未実装なのかを確認することができます。
