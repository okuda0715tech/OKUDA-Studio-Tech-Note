# ブランチ戦略

## 同時並行作業が発生する可能性がある場合にブランチを切る

ブランチを分けると、樹形図上で別の枝が生えます。そのため、別の枝として分離して、コミット履歴を見やすくすることがブランチを分ける目的だと思われがちです。たしかに、ブランチが分かれることで、コミット履歴が見やすくなることは多々あります。しかし、ブランチを分けても枝がわかれないことがあります。そのため、枝を分けて、履歴を見やすくすることは、ブランチを分ける本質ではないと考えられます。

ブランチを分けても樹形図上で枝が分かれないパターンは、「分けたブランチをマージするまでの間に、元のブランチが一度もコミットされていない場合」です。この場合、マージすると、元のブランチと派生ブランチが一本の線になります。

では、ブランチを分ける本質的な意味は何でしょうか？

ブランチを分ける本質的な意味は、「同時並行で進行する可能性のある複数の種類の修正を分離することで、衝突を回避すること」です。

例えば、機能追加用の feature ブランチを生やしたとします。新しい機能を実装中に、リリース済みのアプリで不具合が検出され、緊急対応が必要になることがあります。その場合、 feature ブランチの作業を一旦停止し、不具合の修正を優先するでしょう。つまり、機能追加と不具合修正の同時並行作業が発生したことになります。この状況で、お互いの修正の衝突が発生しないようにして、作業するために、ブランチを分けることになります。

ただし、枝を生やしてからマージするまでに、マージ先のブランチに一度もコミットがなかったとしても、強制的にブランチを枝分かれさせる方法もあります。これは、 non fast-forward マージと呼ばれるものです。強制的にマージコミットを作成することで、ブランチを樹形図上で必ず分岐させることができます。詳しくは、 [マージ時に必ず樹形図を分岐させる方法](マージ時に必ず樹形図を分岐させる方法.md) を参照してください。


### ブランチをわけなくてもよい場合

上記の本質を理解していると、ブランチをわけてもあまり意味がない場合もわかってきます。

例えば、新しい機能の実装中に、その部分をリファクタリングしたくなったとします。新しい機能であるため、既存コードには存在しない部分をリファクタリングするとします。その場合、自分は一人しかいないため、新機能の実装と、リファクタリングが同時並行で実施される可能性は非常に低いです。そうなれば、わざわざ新機能とリファクタリングを別のブランチにする必要はなく、一つのブランチ内で両方を実施して問題ないです。


## 指摘対応ごとにブランチを切る

コードレビューで指摘が発生するたびに新しいブランチを切ると、派生元のブランチがどのコミットをポイントしているか明確になります。そのため、指摘対応の開始地点がわかりやすくなります。これにより、レビューする側の人は、どのブランチが指摘対応ブランチなのかを教えてもらうだけで、どのコミットからどのコミットまでが指摘対応なのかがすぐにわかります。

この場合、指摘対応が完了したら派生元のブランチにマージします。
